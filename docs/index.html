Outage-Proof Livestream

Keep your church livestream on air when the internet drops

OBS records to a file on disk and never touches the network. This service pushes that file to your relay -- and when the connection dies, it picks up from the exact byte and catches up faster than realtime. Your viewers see a gap-free stream. You lose nothing.

The stream drops. The recording does not.

It happens mid-sermon, every time it happens.

The internet blinks, the router hiccups, or the relay hiccups -- and the livestream just stops. Nobody in the room notices. The pastor keeps preaching. The recording on the church PC keeps rolling, perfectly fine.

But the people watching from home lost that part. Not paused -- gone. The exact minute someone needed to hear did not make it, and there is no getting it back once the stream has moved on.

That gap is the whole problem this service exists to close.

The disk file is the buffer

No cloud, no queue, no magic -- just a file that never stops growing.

OBS writes the service to a local .ts file and never talks to the network itself. A small pusher service tails that growing file and sends it on to your relay.

If the connection drops, the pusher does not lose its place. It resumes from the exact byte offset it left off at, and sends faster than realtime until it has caught back up -- so the YouTube DVR stays gapless even after a multi-minute outage.

Nothing is ever skipped, and nothing is ever reordered. The pusher reads the file strictly in consecutive byte order, which is what makes the output gapless in the first place.

Set it up

Two machines, two short setups. Neither one needs anything exotic.

Windows (the church PC)

  1. 1.

    Clone this repository onto the machine running OBS.

    git clone https://github.com/logingrupa/outage-proof-livestream.git
  2. 2.

    Copy .env.example to .env and set RECORDING_FOLDER_PATH (the folder OBS records .ts files into), RELAY_HOST, and RELAY_PORT (your VPS relay’s address and port).

    copy .env.example .env
  3. 3.

    Run install.ps1 from an elevated (Administrator) PowerShell prompt. It registers a Windows Scheduled Task that starts the supervisor at boot -- idle, streaming nothing until you press Start on the dashboard.

    .\install.ps1

VPS (the relay)

  1. 1.

    Copy the tools/vps/ folder to the VPS.

  2. 2.

    Run it once with DRYRUN=1 to preview what it would do, with zero side effects.

    DRYRUN=1 bash tools/vps/setup-vps.sh
  3. 3.

    Run it for real. It installs ffmpeg if missing, creates a chmod-600 env file, and installs and starts the relay service listening on the default port.

    bash tools/vps/setup-vps.sh
  4. 4.

    Add your YouTube ingest URL to the env file it created.

    echo 'YT_URL=rtmps://a.rtmp.youtube.com/live2/YOUR-STREAM-KEY' | sudo tee -a /etc/default/outage-proof-relay
  5. 5.

    Restart the relay service so it picks up the new ingest URL.

    sudo systemctl restart outage-proof-relay.service
  6. 6.

    Open the relay port (8890 by default) in the VPS firewall -- TCP for the default transport, UDP if you chose SRT.

Choosing a transport

Two ways to get bytes from the church PC to the relay.

TransportStatusNotes
tcpDefault, recommendedPlain TCP; the kernel's own congestion control paces the send. No libsrt build needed on either end. Works through NAT with a single forwarded port.
srtAdvancedNeeds a libsrt-enabled ffmpeg on both ends. Rides UDP. Requires transtype=file on both the pusher and the relay listener -- a mismatch is rejected at handshake.

tcp is the default because an uncontrolled UDP path can let SRT's file-mode retransmission feed back on itself: packet loss triggers retransmits, retransmits add more load, more load causes more loss. TCP's own congestion control has no such failure mode, so it is the safer default for anyone starting from scratch. srt remains available for setups that specifically need it, as long as both ends are kept in file mode.

What you need

Church PC

  • Windows 10 or newer
  • PowerShell 7.4+

Relay

We built this because our own Sunday stream kept dying. Two WANs, a bonded router -- and it still dropped. Every drop was a piece of the sermon nobody would ever hear. So we made the recording on disk the source of truth, and taught the pusher to catch up.
